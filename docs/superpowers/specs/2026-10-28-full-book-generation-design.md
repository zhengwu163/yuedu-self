# 整本生成与读音词典设计（2026-10-28，用户已确认方向）

## 1. 目标与用户已定事项

- 用户在书籍详情页或书架长按菜单选「整本生成」，家里电脑在后台生成整本书的多角色音频。
- 生成顺序：先从当前阅读章往后到书末，再回头补第 1 章到当前章前一章。
- 手机把正文交给电脑后即可离开；说话人分析、人物表、音色绑定、合成都在电脑上完成（用户 2026-10-28 选定）。
- 手机回到家庭 Wi‑Fi 时，自动下载所有已生成、尚未下载的章节。
- 电脑在手机下载完某章后保留该章音频 30 天，之后自动删除；产品稳定后再缩短（用户 2026-10-28 定）。
- 整本任务执行期间，电脑不响应手机的逐章生成请求（用户 2026-10-28 接受）。
- 全本地；手机与电脑只走局域网 + 令牌。现有逐章模式的行为不变。

## 2. 现状与差距

- 现在由手机驱动生成：手机持有运行时租约，逐段同步调用分析和合成接口
  （`NovelAudioPreparationEnvironment.acquireBatch`、`NovelAudioDownloadCoordinator.downloadPlan`）。
  生成期间手机必须在线、App 进程存活。一本 300 章的书按 RTF 1.6 要约 6 天，手机做不到。
- 服务端没有作品、任务或持久化的概念，只有无状态接口和一个运行时租约（`scripts/novel_audio_server/api.py`）。
- 只有手机能取正文：书源抓取、替换净化、`ContentProcessor` 都在手机上。
- 分析编排、人物表与音色绑定现在都在手机上，已经真机验证：
  - `NovelAudioAnalysisCoordinator.analyze`：分批（每批最多 64 单元、4000 UTF-16 字符）、携带上下文与最近归属、
    临时人物 ID 转正式 ID、按发言提示校正、绑定音色。
  - `NovelAudioCharacterRegistry.resolve`：别名归一、新人物建档、别名更新、排除「师父/哥哥/他」类称谓。
  - `NovelAudioSpeakerResolver.explicitSpeaker`：引语前后的「某某说」类提示覆盖模型判断。
  - `NovelAudioVoiceBindingRegistry.bind`：旁白用保留音色，对白排除已用音色，性别只在已知时约束，手动绑定优先。
- 切分 `TextUnitParser.splitForSynthesis` 只依赖单元文字和段长上限，与说话人无关，可以在分析前做。
- 段 ID 由文字、正文位置、说话人、音色、绑定修订号算出（`NovelAudioSegmentIntent.create`），分析前无法确定。
- 播放只认手机本地 READY 的计划与音频，并用快照散列校验正文身份（`NovelAudioLocalFirstGate`）。

结论：手机只做取正文和切分，上传「单元文字 + 每个单元切好的若干小段文字」；电脑把上面四块分析与绑定逻辑
移植成 Python，在任务里逐章执行并合成。手机下载时拿到每个单元的说话人、新人物、音色和每小段的音频，
用现有 `NovelAudioPlanFactory.create` 在本地生成计划，按顺序把小段音频对到计划的段上。
播放、高亮、续播路径不变。

## 3. 总体流程

阶段一：上传（手机需在家庭 Wi‑Fi）
1. 用户确认后，手机创建整本任务，同时上传该作品已有的人物表、别名和音色绑定（包括手动绑定）。
2. 手机在前台服务中按「当前章 → 书末 → 第 1 章 → 当前章前一章」逐章：取正文快照 → 解析单元 →
   按电脑声明的段长上限把每个单元切成小段 → 上传单元列表（单元 ID、单元文字、小段文字列表）与快照散列。
3. 本地书（TXT/EPUB）每章只需毫秒到秒级，300 章预计几分钟；在线书源的书受书源速度限制。
   中途断网、退出或重启后，从未上传的章节继续。上传完成后手机即可离开。

阶段二：电脑逐章处理（无需手机）
4. 电脑按上传顺序逐章：分批分析说话人 → 校正 → 新人物建档 → 绑定音色 → 合成该章所有小段 → 标记可下载。
   收到第一章就开始，所以当前章最先完成。
5. 人物表在整个任务内共享，后面章节复用前面章节建立的人物与音色。

阶段三：同步（手机回到家庭 Wi‑Fi）
6. 手机定期检查任务状态，对每个新完成的章节：
   取该章结果（单元说话人、新人物、别名更新、音色绑定、小段音频清单）→ 新人物和别名写入手机人物表
   （走现有 `CharacterRegistry.resolve`，与收到一次分析响应的处理相同）→ 用快照与说话人生成计划 →
   逐段下载音频、校验 SHA‑256 与解码 → 写入音频表 → 计划变为 READY → 告知电脑该章已下载。
7. 电脑记录每章的下载时间，30 天后删除该章音频与正文。

## 4. 电脑端（`scripts/novel-audio-local/`）

新文件，尽量不改现有文件：
- `book_jobs_store.py`：SQLite 存储（Python 标准库 sqlite3，`state/book-jobs.sqlite3`）与音频目录（`state/book-jobs/<jobId>/`）。
- `book_jobs_analysis.py`：移植分析编排、人物表、发言提示校正、音色绑定（见第 6 节）。
- `book_jobs_runner.py`：单线程执行器。
- `book_jobs_api.py`：HTTP 路由，`scripts/novel_audio_server/api.py` 只增加一个分发入口。

存储内容：
- 任务：作品 ID、书名、状态（上传中 / 执行中 / 已暂停 / 已完成 / 已取消）、profile、段长上限、创建时间。
- 人物与别名、音色绑定：初始值来自手机上传，执行中由分析补充。
- 章节：章节 ID、序号、上传顺序、快照散列、状态（待处理 / 分析中 / 合成中 / 已完成 / 失败）、失败类型、下载时间。
- 单元与小段：单元 ID、单元文字、说话人；小段序号、文字、音色 ID、音频文件、SHA‑256、大小、类型、`X-TTS-Profile`。
- 正文只存服务根目录内，不进日志、不进源码包。

执行器：
- 复用现有 Worker 进程、资源门禁与租约逻辑，以内部身份持有运行时；任务完成、暂停或取消后释放并卸载模型。
- 一次只执行一个整本任务，后提交的排队。
- 有整本任务在执行时，手机的普通逐章请求返回 429 和固定错误类型 `book_job_running`，手机提示「电脑正在整本生成」。
- 电脑重启后从未完成的章节继续：分析结果已保存的章节不重新分析；已保存且校验通过的小段音频不重做。
- 托盘菜单增加「暂停整本生成 / 继续」。
- 每天检查一次过期音频（已下载满 30 天），删除文件与正文；保留期为配置项 `bookJobs.retentionDaysAfterDownload`，默认 30。

新增接口（都需要令牌，单次 JSON 仍不超过 2 MiB，错误只返回固定类型）：
- `POST /v1/book-jobs`：创建任务（作品 ID、书名、预计章数、现有人物 / 别名 / 绑定）。返回任务 ID 与段长上限。
- `PUT /v1/book-jobs/{jobId}/chapters/{chapterId}`：上传一章（序号、快照散列、单元与小段文字）。同一散列重复上传为幂等。
- `POST /v1/book-jobs/{jobId}/uploaded`：标记全部章节已上传。
- `GET /v1/book-jobs/{jobId}`：任务状态、每章状态、已完成章数、最近 RTF 与每章耗时。
- `GET /v1/book-jobs/{jobId}/chapters/{chapterId}`：该章结果（说话人、新人物、别名更新、绑定、小段音频清单）。
- `GET /v1/book-jobs/{jobId}/audio/{audioId}`：单段音频本体。
- `POST /v1/book-jobs/{jobId}/chapters/{chapterId}/downloaded`：手机确认已下载，开始计算保留期。
- `POST /v1/book-jobs/{jobId}/pause|resume|cancel`，`DELETE /v1/book-jobs/{jobId}`。
- `PUT /v1/book-jobs/{jobId}/voice-bindings`：手机上手动改音色后同步，只影响之后处理的章节。

## 5. 手机端

入口：
- 书籍详情页与书架长按菜单新增「整本生成」。书籍详情有经典、Modern、Compose 三套页面，书架有两种样式和 Compose 列表，
  每一处入口都要过主题一致性四道卡点（`docs/project-rules/theme-consistency-iron-rule.md`）。
- 确认框显示：章数、按电脑最近速度估算的总时长、预计占用手机空间（Opus 48 kbps 约每小时 22 MB）、
  上传阶段需要连着家里 Wi‑Fi。

数据：
- Room 新增整本任务表（书、任务 ID、服务端身份、上传进度、状态、最后同步时间）和章节同步表
  （章节序号、快照散列、上传状态、下载状态）。需要数据库版本升级、迁移与迁移测试。
- 现有计划、段、音频、人物、绑定表结构不变；整本任务产出的计划 retention 用 `PINNED`，不被 AUTO 清理。

阶段一上传：
- 前台服务 + 通知栏进度。复用 `NovelAudioChapterSnapshotLoader` 取快照、`TextUnitParser.parse` 解析单元、
  `TextUnitParser.splitForSynthesis` 切小段，不调用分析接口。
- 只在 Wi‑Fi 下执行；网络断开时暂停，恢复后继续。

阶段三同步：
- 系统周期任务（JobScheduler，每 30 分钟、仅不计流量网络，每次最多 8 分钟）+ App 启动时 + 打开整本进度时各检查一次。
  能连上电脑才视为在家；连不上就安静跳过。用 JobScheduler 而不是 WorkManager：效果相同，且不新增依赖。
- 导入一章：重新取该章快照，散列与上传时不一致（书源内容变了）则不导入，标记该章需要重新生成。
  一致则把电脑结果当作分析结果，生成计划；计划的段与电脑小段按（单元 ID，小段序号）一一对应，并校验文字相同，
  任何不一致都拒绝导入该章并记录固定错误类型。
- 音频沿用 `NovelAudioArtifactStore.commit` 与 `NovelAudioRepository.saveArtifact` 的校验与写入。
- 播放到尚未导入的整本任务章节时：先尝试立即同步该章；电脑还没生成完就暂停并提示「这一章电脑还在生成」。
- 手动改音色：已下载的章节保留原音色；同步新绑定给电脑，之后处理的章节使用新音色。
  只同步旁白和建任务前已有的人物（两边 ID 相同）；电脑在任务中新建的人物，手机上改音色暂不回传。

管理：书籍详情显示整本进度（已生成 / 已下载 / 总章数），可暂停、继续、取消、删除。

## 6. 移植范围与一致性保证

从 Kotlin 移植到 Python 的逻辑，以现有 Kotlin 为准，行为不变：
- `NovelAudioAnalysisCoordinator.analyze` 的分批、上下文裁剪、最近归属、临时 ID 转换、发言提示校正与绑定顺序。
- `NovelAudioCharacterRegistry.resolve` 与 `normalizeAlias`、称谓排除；人物合并记录（merge）只读使用，不在电脑上新建合并。
- `NovelAudioSpeakerResolver.explicitSpeaker` 的正则与 80 字窗口。
- `NovelAudioVoiceBindingRegistry.bind` 与 `bindVoices` 的旁白保留、已用音色排除、性别约束规则。

一致性测试：从现有 Kotlin 单测中整理一组输入输出用例（JSON），Python 端跑同一组用例，结果必须完全相同；
以后改任一侧逻辑都要同时更新这组用例。手机导入时人物表仍由 Kotlin 代码最终写入，电脑只提出建议。

当前状态：用例在 `scripts/novel-audio-local/fixtures/book_jobs_parity.json`，Python 端由
`test_book_jobs_analysis.py` 读取，Kotlin 端由 `NovelAudioBookJobParityTest` 读取同一文件，两侧都全部通过。

## 7. 读音词典

放在电脑端，合成前替换文字；对所有引擎、整本任务和逐章模式都生效。手机上的正文、高亮和正文位置不受影响，
因为替换只作用于送给模型的文字。

- 文件：服务根目录下 `config/pronunciation.json`（不进仓库）。条目：原文、替换为、范围（全局或某个作品 ID）、备注。
- 替换方式：用同音字，例如「单牧」→「善牧」、「曾晚」→「增晚」、「解老板」→「谢老板」。
  整词精确匹配、长词优先，第一版不支持正则。部分引擎支持拼音标注，留待选定引擎后再加。
- 版本：词典内容散列记录在每段音频的元数据里。改了词典不会自动重做已生成的音频；用户可对指定章节选择重新生成。
- 编辑：第一版在电脑上直接改文件，托盘菜单提供「打开读音词典」，保存后下一段合成即生效。
  手机端编辑界面放到第二版，需要过主题一致性卡点。
- 可选辅助：分析时对含多音字姓氏的人名（曾、单、解、仇、朴、区、查、尉迟等）给出提示清单，由用户确认后写入词典。
- 基准文本 `scripts/novel-audio-bench/fixtures/`（分支 `chore/bench-fixtures`）已包含这些检查点，可直接用来验收。
- 当前只接到整本任务的合成上；逐章模式（`api.py` 的 `/v1/tts/synthesize`）暂不替换，
  等 Windows agent 的批量合成改动合入后再接，避免同时改同一段代码。

## 8. 与 Windows agent 当前任务的关系

- Windows agent 正在按路线图做基准、VoiceStudio 评估和 Qwen3-TTS 批量合成，很可能会改合成后端和 `api.py`。
- 为减少冲突：电脑端新代码放在新文件里，对 `api.py` 只增加一个分发入口；执行器先逐段调用现有合成，
  等批量合成合入主线后再切换。
- 段长上限由服务端声明。整本任务没有 30 秒单次请求的限制，可以用更长的段，具体值等段长实测结果再定，先沿用现有 50 字。

## 9. 分步交付

当前进度（分支 `feat/full-book-jobs`）：第 1、2 步代码完成，Python 与 JVM 测试通过，Room 迁移测试已编译但需真机运行；
第 3 步真机验收未做。入口说明：书架长按本身就进入书籍详情，所以只在三套书籍详情页加了入口；
确认框的时长与空间按书籍字数估算（每分钟约 250 字、每小时约 22 MB），字数未知时不显示。

1. 电脑端：存储、接口、执行器、移植的分析与绑定、读音词典、30 天清理；假后端测试与 Kotlin/Python 一致性用例（Mac 上可完成）。
2. 手机端：数据库迁移、上传前台服务、同步与导入、入口与进度界面；JVM 测试 + Room 测试（Mac 上可完成，可出 debug 包）。
3. 真机验收（需要 Windows 电脑与手机）：用基准三章和一本原创 10 章测试书验证
   上传完立刻断开 Wi‑Fi、电脑继续生成、回家后自动下载、飞行模式连续播放、杀进程续播、人物与音色前后章一致；
   记录上传耗时、每章分析与合成耗时。
4. 第二版：手机端读音词典编辑、多音字人名提示、多本书排队界面。
