# 整本生成与读音词典设计（2026-10-28，待用户确认）

## 1. 目标与用户已定事项

- 用户在书籍详情页或书架长按菜单选「整本生成」，家里电脑在后台生成整本书的多角色音频。
- 生成顺序：先从当前阅读章往后到书末，再回头补第 1 章到当前章前一章。
- 手机回到家庭 Wi‑Fi 时，自动下载所有已生成、尚未下载的章节。
- 全本地；手机与电脑只走局域网 + 令牌。
- 现有逐章模式（当前章、AUTO 后三章、PINNED 手动下载）的行为不变。

## 2. 现状与差距

- 现在由手机驱动生成：手机持有运行时租约，逐段同步调用合成接口
  （`NovelAudioPreparationEnvironment.acquireBatch`、`NovelAudioDownloadCoordinator.downloadPlan`）。
  生成期间手机必须在线、App 进程存活。一本 300 章的书按 RTF 1.6 要约 6 天，手机做不到。
- 一章的耗时绝大部分在合成；正文快照、说话人分析、音色绑定、切分加起来每章只需十几秒到几十秒。
- 服务端没有作品、任务或持久化的概念，只有无状态接口和一个运行时租约（`scripts/novel_audio_server/api.py`）。
- 只有手机能取正文：书源抓取、替换净化、`ContentProcessor` 都在手机上。
- 说话人校正、别名过滤、人物表和手动音色绑定都在手机上（`NovelAudioAnalysisCoordinator`、
  `NovelAudioCharacterRegistry`、`NovelAudioRoomCharacterStore`），已经真机验证。
- 播放只认手机本地 READY 的计划与音频，并用快照散列校验正文身份（`NovelAudioLocalFirstGate`）。

结论：只把「合成」交给电脑排队执行。手机照旧取正文、分析、绑定音色、生成计划，计划里每一段的文字、
音色和正文位置都和现在一样；不同的只是段音频不再当场合成，而是事后从电脑下载。
这样不需要在电脑上重写一遍已经验证过的分析与人物逻辑，播放、高亮、续播路径也都不变。

## 3. 总体流程

阶段一：手机在线，逐章建计划并上传
1. 用户确认后，手机创建整本任务，在前台服务中按「当前章 → 书末 → 第 1 章 → 当前章前一章」逐章执行：
   取正文快照 → 分析说话人 → 绑定音色 → 按电脑声明的段长上限切分 → 保存计划（新状态 `WAITING_REMOTE`）
   → 把该章所有段的段 ID、文字、音色 ID 上传到任务。
2. 电脑收到第一章就开始合成，合成顺序等于上传顺序，所以当前章最先完成，用户很快就能开始听。
   阶段一的分析请求与后台合成共用同一个已加载的模型进程，分析优先：最多等当前这一段合成完（几秒）就插队执行。
3. 阶段一耗时约为「章数 × 每章分析时间」，300 章预计一到两小时（待实测）。
   中途断网、退出或重启后，从未上传的章节继续，已上传的章节不重做。

阶段二：手机可离开，电脑逐章合成
4. 电脑按上传顺序逐章合成，完成后标记该章可下载。
5. 手机在家庭 Wi‑Fi 下定期检查任务状态，下载新完成的章节：逐段下载音频、校验 SHA‑256 与解码，
   按现有方式写入音频表；一章全部就绪后计划变为 READY，播放即可离线使用。
6. 电脑保留已合成的音频，直到用户在手机上删除该任务。

## 4. 电脑端（`scripts/novel-audio-local/`）

存储：`state/book-jobs.sqlite3`（Python 标准库 sqlite3）+ `state/book-jobs/<jobId>/audio/`。
- 任务：作品 ID、书名、状态（建立中 / 合成中 / 已暂停 / 已完成 / 已取消）、创建时间、所用 profile。
- 章节：章节 ID、序号、上传顺序、正文散列、状态（待合成 / 合成中 / 已完成 / 失败）、失败类型。
- 段：段 ID、合成文字、音色 ID、语速、音频文件、SHA‑256、大小、类型、`X-TTS-Profile`。
- 合成文字只存在服务根目录内，不进日志、不进源码包；删除任务时删除该任务的全部文件。

执行器：
- 单个后台执行器，复用现有 Worker 进程与资源门禁。执行器以内部身份持有运行时，有任务时保持模型加载，
  任务完成、暂停或取消后释放并卸载（与现有「批次后卸载」一致）。
- 队列两级：任务内的分析请求优先，合成段次之，以段为切换点。
- 一次只执行一个整本任务，后提交的排队。
- 有整本任务在执行时，手机的普通逐章请求返回 429 和固定错误类型 `book_job_running`，手机提示「电脑正在整本生成」。
- 电脑重启后从未完成的段继续，已保存且校验通过的音频不重做。
- 托盘菜单增加「暂停整本生成 / 继续」。

新增接口（都需要令牌，单次 JSON 仍不超过 2 MiB，错误只返回固定类型）：
- `POST /v1/book-jobs`：创建任务（作品 ID、书名、预计章数）。返回任务 ID 与段长上限。
- `POST /v1/book-jobs/{jobId}/analyze`：与 `/v1/chapter/analyze` 请求响应完全相同，只是在任务的执行器里插队执行。
- `PUT /v1/book-jobs/{jobId}/chapters/{chapterId}`：上传一章（序号、正文散列、段列表）。重复上传同一散列为幂等。
- `GET /v1/book-jobs/{jobId}`：任务状态、每章状态、已完成章数、最近 RTF 与每章耗时。
- `GET /v1/book-jobs/{jobId}/chapters/{chapterId}`：该章的段音频清单（段 ID、音频 ID、SHA‑256、大小、类型、profile）。
- `GET /v1/book-jobs/{jobId}/audio/{audioId}`：单段音频本体。
- `POST /v1/book-jobs/{jobId}/pause|resume|cancel`，`DELETE /v1/book-jobs/{jobId}`。
- `POST /v1/voices/match` 不需要租约（`scripts/novel_audio_server/api.py` 直接处理），阶段一照常调用。

## 5. 手机端

入口：
- 书籍详情页与书架长按菜单新增「整本生成」。书籍详情有经典、Modern、Compose 三套页面，书架有两种样式和 Compose 列表，
  每一处入口都要过主题一致性四道卡点（`docs/project-rules/theme-consistency-iron-rule.md`）。
- 确认框显示：章数、按电脑最近速度估算的总时长、预计占用手机空间（Opus 48 kbps 约每小时 22 MB）。

数据：
- Room 新增整本任务表：书、任务 ID、服务端身份、上传进度、状态、最后同步时间。需要数据库版本升级与迁移测试。
- 计划状态新增 `WAITING_REMOTE`；retention 用 `PINNED`，不被 AUTO 清理。
- 计划、段、音频表结构不变，播放与离线校验逻辑不变。

阶段一执行：
- 前台服务 + 通知栏进度，复用 `NovelAudioPreparationEnvironment` 的快照、分析、绑定、切分代码，
  把「下载缺段」换成「上传段列表」。
- 在线书源的书需要逐章抓取正文，速度受书源限制；确认框要说明。
- 只在 Wi‑Fi 下执行；网络断开时暂停，恢复后继续。

阶段二同步：
- WorkManager 周期任务（不计流量的网络）+ App 启动时 + 打开书籍时各检查一次。
  能连上电脑才视为在家；连不上就安静跳过，不提示错误。
- 下载沿用 `NovelAudioArtifactStore.commit` 与 `NovelAudioRepository.saveArtifact` 的校验；
  正文散列与手机当前快照不一致的章节（书源内容变了）不入库，标记为需要重新生成。
- 手动改音色：已下载的章节保留原音色；未合成的章节由手机重新上传该章段列表。
- 播放到还在 `WAITING_REMOTE` 的章节时：先尝试立即同步该章；电脑还没生成完就暂停并提示「这一章电脑还在生成」，
  不退回逐章生成。

管理：
- 书籍详情显示整本进度（已生成 / 已下载 / 总章数），可暂停、继续、取消、删除。

## 6. 读音词典

放在电脑端，合成前替换文字；对所有引擎、整本任务和逐章模式都生效。手机上的正文、高亮和正文位置不受影响，
因为替换只作用于送给模型的文字。

- 文件：服务根目录下 `config/pronunciation.json`（不进仓库）。条目：原文、替换为、范围（全局或某个作品 ID）、备注。
- 替换方式：用同音字，例如「单牧」→「善牧」、「曾晚」→「增晚」、「解老板」→「谢老板」。
  整词精确匹配、长词优先，第一版不支持正则。部分引擎支持拼音标注，留待选定引擎后再加。
- 版本：词典内容散列记录在每段音频的元数据里。改了词典不会自动重做已生成的音频；
  用户可对指定章节选择重新生成。
- 编辑：第一版在电脑上直接改文件，托盘菜单提供「打开读音词典」，保存后下一段合成即生效。
  手机端编辑界面放到第二版，需要过主题一致性卡点。
- 可选辅助：分析时对含多音字姓氏的人名（曾、单、解、仇、朴、区、查、尉迟等）给出提示清单，由用户确认后写入词典。
- 基准文本 `scripts/novel-audio-bench/fixtures/`（分支 `chore/bench-fixtures`）已包含这些检查点，可直接用来验收。

## 7. 与 Windows agent 当前任务的关系

- Windows agent 正在按路线图做基准、VoiceStudio 评估和 Qwen3-TTS 批量合成，很可能会改合成后端和 `scripts/novel_audio_server/api.py`。
  整本任务也要在 `api.py` 增加路由，并在执行器里调用合成。
- 为减少冲突：电脑端新代码放在新文件里，对 `api.py` 只增加一个路由分发入口；
  执行器先逐段调用现有合成，等批量合成合入主线后再切换。
- 段长上限由服务端声明。整本任务没有 30 秒单次请求的限制，可以用更长的段，具体值等 Windows agent 的段长实测结果再定，
  先沿用现有 50 字。

## 8. 分步交付

1. 电脑端：任务存储、接口、执行器、读音词典，用假后端写测试（Mac 上可完成）。
2. 手机端：数据库迁移、阶段一前台服务、上传、阶段二同步、入口与进度界面，JVM 测试 + Room 测试（Mac 上可完成，可出 debug 包）。
3. 真机验收（需要 Windows 电脑与手机）：用基准三章和一本原创 10 章测试书，验证
   阶段一完成后断开 Wi‑Fi、电脑继续生成、回家后自动下载、飞行模式连续播放、杀进程续播；记录阶段一耗时和每章生成耗时。
4. 第二版：手机端读音词典编辑、多音字人名提示、多本书排队界面。

## 9. 不在本设计范围内

- 实时边听边生成（按路线图第 7 节，等速度达标再做）。
- 把分析搬到电脑端。
- 离家时接收新章节（需要隧道，改变网络红线）。

## 10. 需要用户确认

- 整体方案：手机负责正文、分析和计划，电脑只排队合成（第 2、3 节）。
- 阶段一需要手机在家庭 Wi‑Fi 下保持约一到两小时（300 章估算），期间显示通知；这一点是否可以接受。
- 整本任务执行期间，电脑不再响应手机的逐章生成请求（第 4 节），只能等整本任务暂停或完成。
- 电脑保留音频直到用户删除任务，一本 300 章的书约 2 GB。
