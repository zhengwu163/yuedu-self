# AI 听书路线图：速度判定、整书模式与远程调试（2026-10-28）

本文是后续迭代的方向依据。现状细节与红线仍以 [AI_AUDIOBOOK_WINDOWS_TAKEOVER.md](AI_AUDIOBOOK_WINDOWS_TAKEOVER.md) 为准；
2026-10-09 之后的实测证据在 `superpowers/plans/2026-10-09-windows-takeover.md`、
`superpowers/plans/2026-10-11-windows-lifecycle-desktop.md` 与 [AI_AUDIOBOOK_FIXED_VOICES.md](AI_AUDIOBOOK_FIXED_VOICES.md)。

## 1. 产品目标与判定线

- 指标：RTF = 合成耗时 ÷ 音频时长。
- 判定（用户 2026-10-28 定）：稳定 RTF ≤ 0.5 才做「边听边生成」；达不到则做「整书后台生成」：
  用户一次提交整本书，电脑逐章生成，每完成一章交付手机。
- 两种模式不是二选一：整书后台模式无论速度都要做，是底座；实时模式在达标后叠加。
  一本 300 章、每章约 3800 字的书约 90 小时音频；RTF 0.5 也要约 45 小时，RTF 1.6 约 6 天。
- 实时模式另需满足：首段等待短（目标待用户定）、全书人物分析提前完成、显存被占时排队而不是失败。
- 分发范围：仅自用/家用（用户 2026-10-28 定）。非商用许可的模型权重可以入选；将来若对外分发须重审许可。
- 全本地：章节分析与语音合成都在本机完成，不用在线模型（用户 2026-10-28 定）。
- 交付含义：当前只走家庭局域网，「推送到手机」实际是手机回到家庭 Wi‑Fi 时自动拉取已完成章节。
  离家期间接收需要隧道（如 Tailscale），这会改变网络红线，须用户另行决定。

## 2. 现状快照（GitHub `feat/local-model-service` @ 495c3d3b，2026-10-24）

已在真机 + 真实本地模型验证：
- 局域网 + 令牌连通；当前章 PINNED → 分析 → 分段合成 → READY → 多角色播放；六章批量全部 READY。
- 飞行模式跨章连听；强杀后恢复续播；AUTO 后三章跨边界滚动续写（短测试章）。
- 固定音色：用 Base 克隆固定样本，替代每次会漂移的 VoiceDesign，用户已试听认可。
- 托盘开关与登录自启注册（真实注销再登录未测）；普通朗读不回归；HTTP 朗读被拒时不再静默跳过。
- 生命周期：保留「每批后立即卸载」。常驻每批约省 20 秒，但批间占约 11 GiB 显存。

未完成：
- 速度不达标：2026-10-09 实测 RTF ≈ 1.6（一章约 3800 字，生成约 28 分钟、播放约 18 分钟）。
  10-10 之后的计时都用短测试章且没记录音频时长，不能据此判断 RTF。
- 整书后台模式、实时模式都未开始。
- 只有源码包，没有含运行时与模型的一键包；iCode `origin/main` 未同步任何听书代码。

## 4. 提速路线（2026-10-28 公开资料调研，均未在本机 5090D 上实测）

当前调用方式：`qwen_backend.py` 用 bf16、未指定 attention，每次调用合成一段约 50 字。
社区在同类显卡上报告 GPU 利用率只有 4–16%，主要耗在大量小 kernel 的启动开销上，不在模型规模。

先不换模型（按顺序试，每步用同一基准量一次）：
1. 一次调用传入 4–8 段（官方 API 接受列表）。QwenLM/Qwen3-TTS PR #380（未合入，作者实测）在 RTX 5090 上测 1.7B Base：
   batch 4 RTF 0.46，batch 8 RTF 0.25。注意同一模型实例多线程并发反而慢（issue #350）。
2. CUDA graphs：`faster-qwen3-tts`（MIT，带 Windows 安装脚本）在 4090 上 1.7B RTF ≈ 0.24。
   它会装 `qwen-tts-hf`，不能与官方 `qwen-tts` 装在同一环境；单条生成，不支持批量。
   PR #380 的 batch 8 + CUDA graphs 组合为 RTF ≈ 0.14。
3. 长段克隆传 `non_streaming_mode=True`（PR #362），否则长文本语速会逐渐变快。
4. 不建议：flash-attn（Windows sm_120 无官方 wheel，实测几乎不提速）；换 0.6B（4090 上 0.21 对 0.24，且没有 VoiceDesign）。
5. vLLM-Omni 已支持 Qwen3-TTS 服务与流式输出，但官方只列 Linux，Windows 上要走 WSL2；
   与「Windows 原生、不用 WSL」的现有约束冲突，留作后备。

换引擎候选（自用，非商用权重可选）：
- OmniVoice：VoiceStudio 的默认引擎，权重 CC-BY-NC。H100 上 batch 1 RTF 0.09，开 FlashInfer 约 0.04。
  Mac M2 上实测 RTF ≈ 1.7、音色差，但 Mac 结果不能代表 5090D。VoiceStudio 是否支持 sm_120 未核实。
- VoxCPM2（Apache-2.0）：4090 上 RTF ≈ 0.30，支持音色设计。
- IndexTTS-2.5（bilibili 许可）：情绪与语速控制强，适合角色对白；未查到绝对 RTF。
- Fun-CosyVoice3（Apache-2.0）：流式；上游固定的旧 torch 跑不了 RTX 50 系。
- GPT-SoVITS：极快（4090 RTF ≈ 0.014），但要为每个音色单独微调，适合少量固定主角。
- Fish Audio：S2-Pro 研究许可；Drama 3 需 48 GB 以上显存，本机放不下。

### 4.1 音色策略

- 多角色需要的是「很多个稳定的声音」，不是每次都现场设计声音。
- 做法：一次性建好音色库（每个音色一段 10–30 秒参考录音 + 对应文字），合成时只用「按参考录音克隆」。
  这就是现在固定音色的做法，VoiceDesign 只作为扩充音色库的工具。
- 因此候选引擎的必要能力是「用参考录音稳定克隆中文」；没有音色设计不是缺点。
  只带少量内置音色、不能克隆的引擎（如 Kokoro）不够用。
- 同一套参考录音可以在不同引擎间复用，换引擎时不用重建音色库。

### 4.2 VoiceStudio 路线（先看 Windows 实际落地，再决定用途）

从本机 VoiceStudio 0.5.6 源码确认（尚未在 Windows 上实测）：
- 引擎注册表 + 插件接口（`backend/plugins/` 放一个文件即可加引擎）；IndexTTS2、MOSS、dots.tts、Confucius4 等
  各用独立 venv，依赖版本冲突已由它处理。
- 空闲自动卸载（默认 15 分钟，可配置）和手动卸载接口 `POST /model/unload/{model_id}`。
- 自带有声书流程：导入 txt/epub/pdf 分章，正文中用 `[voice:名字]` 标注角色，按章渲染，可断点续跑，已完成章节有缓存。
  它不会自动识别说话人，角色标注仍需要我们的 9B 分析来生成。
- Qwen3-TTS 只在 Mac 的 MLX 后端里有，Windows/CUDA 上没有；要用现有固定音色需自己写插件。
- 参考分支 `feat/ai-audiobook-voicestudio` 已有 VoiceStudio 适配器（05dcf6de 起），可作为接入起点。
- 版本固定使用，升级前先在基准上复测，没有收益就不升级。

与「直接下载模型自己跑」的分工：
- VoiceStudio 适合初筛：装好就能用同一套参考录音试多个引擎，试听方便，通过适配器还能直接在手机上端到端听。
- 直接部署适合精测与优化：能用批处理、CUDA graphs 等手段把速度压到极限，测出来的是模型真实上限。
  VoiceStudio 测得慢，不等于模型本身慢。

架构决定（2026-10-28，用户委托判断）：自有服务做主体，VoiceStudio 只作为可选的语音合成后端，不 fork、不改它的源码。
- 手机端依赖逐段音频与正文精确位置（高亮、角色气泡、续播位置），这些已在真机验证。
  VoiceStudio 的有声书流程按章输出 m4b，没有逐段与正文的对应关系，改成我们需要的形态不是小改动。
- VoiceStudio 不识别说话人，角色标注仍要靠我们的 9B 分析；它将来是否会做角色记录与分配无法预知，不作为规划依据。
- 速度是决定性约束：跨段批处理与 CUDA graphs 只能在自有服务里做；VoiceStudio 的生成接口一次处理一段文本。
- VoiceStudio 后端约 7 万行、AGPL-3.0、几周一个版本（10-26 已到 0.5.7），fork 后每次跟进上游都要合并冲突。
- 自有服务已有租约、显存门禁、卸载与取消清理，并经真机验证。
- 接法：自有服务的合成适配器通过 HTTP 调用固定版本的 VoiceStudio（参考分支已有适配器），
  一个合成后端可以只用 Qwen3-TTS 原生、只用 VoiceStudio 的某个引擎，或两者都配置、按 profile 切换。
- 重新考虑的条件：某个引擎只能经 VoiceStudio 跑，且经它调用的速度达标；或必须修改它的内部（如取消不中止）才能用。
  届时优先提 PR 给上游，其次在固定版本上保留一个最小补丁文件，仍不整体 fork。
- 可以借鉴它的整书任务与断点续跑思路（按内容缓存已完成章节、resume 清单），在自有服务中实现。

落地评估要回答：
- 哪些引擎在 5090D（sm_120）上能跑；每个引擎在同一基准上的 RTF、首段等待、峰值显存。
- 长章（100 段以上）连续合成是否稳定；卸载后显存是否回落；客户端取消后是否停止生成
  （Mac 上实测：放弃一段长文本后它不中止生成，下一句短文本排队约 35 秒）。
- 与我们的 Worker 共用显卡时如何互斥（不能同时加载）。
- 用同一套固定参考录音的盲听样本。

## 5. 远程调试：Windows 模型服务 + GitHub 仓库

目标：在其他电脑上调用 Windows 上的模型，持续修改调试。

分层：
- Windows 模型主机只做一件事：持有模型，按 v1 + runtime 接口提供分析与合成。
- GitHub 是唯一代码来源。任何机器改代码 → 推到分支 → Windows 按指定 commit 部署。
- 其他机器只是客户端：手机 debug 包、Mac 上的 Android 模拟器、或直接调接口的 Python 脚本。

代码流转：
1. 开发机修改并推到 `feat/local-model-service`（或从它拉出的短期分支）。
2. Windows 上运行部署脚本：拉取指定 commit → 跑服务端测试 → 停旧服务、确认租约释放 → 启动新服务 → 自检。
   失败则回到上一个已知可用的 commit。
3. `/v1/health` 返回当前 commit 与 profile，客户端能确认自己调的是哪个版本。（目前服务端没有返回代码 commit 的字段，需新增。）
4. 不用 GitHub Actions 自托管 runner：仓库公开，别人提交的 PR 可能在这台电脑上执行代码。
   无 GPU 的单测可以放在 GitHub 托管 runner 上跑。

连接方式：
- 同一局域网：直接 `http://<Windows 局域网 IP>:<端口>` + 令牌，与手机相同。
- 离家调试：Tailscale 一类组网工具，只放行组网网段，不做路由器端口映射。是否放开，须用户决定。
- 远程操作 Windows：Windows 自带 OpenSSH Server，只监听局域网或组网网段，只允许密钥登录。

基准与调试工具：
- 增加一个只读基准脚本：固定原创文本、固定音色、固定段长与 batch，
  输出 RTF、首段等待、峰值显存和样本音频。任何机器都能通过接口触发，结果按引擎与 commit 归档。
- 增加批量合成接口（一次多段），否则服务端批处理优化传不到客户端。

红线不变：令牌与 Key 只存在本机配置；正文与模型输出不进日志和提交；推送前扫描密钥。

## 6. 尚未覆盖、需要补齐的部分

- 生成调度要从手机搬到电脑：现在手机逐段调用接口，生成期间手机必须在线且 App 进程存活。
  整书要跑几十小时，必须改成电脑端任务队列（持久化、断点续跑、按章完成状态），手机只提交和拉取。
- 全书人物表：现在按章分析，整书模式应先做全书人物与别名预扫，固定角色和音色，避免后面章节重新建角。
- 中文读音：多音字、人名、数字与英文的读法需要可编辑的发音词典，长书里会反复出现。
- 存储：服务端输出 Opus 48 kbps 单声道（`audio.py`），每小时约 22 MB，90 小时音频约 1.9 GB；
  手机端需要按书清理与空间提示，或评估降到 24–32 kbps 的听感。
- GPU 排期：长时间满载要考虑夜间运行、与 ComfyUI 等程序抢显存时排队、温度与功耗。
- 文档：TAKEOVER 与 PROGRESS 停在 10-09，最新证据散在计划文件里；每个里程碑要回写同一份状态文档。
- 质量验收：目前只有人耳主观判断，应固定一组样章与打分项（角色区分、音量、读音错误数、语速）。
- 全本地：实时模式只能靠本地提速或换本地引擎实现，不把在线 TTS 作为备选。

## 7. 迭代顺序（2026-10-28 按用户意见调整：先看 VoiceStudio 在 Windows 上的真实表现）

0. 打基础：基准脚本、`/v1/health` 返回 commit、Windows 部署脚本、状态文档回写；用当前 Qwen3-TTS 跑出基线。
1. VoiceStudio 落地评估：按第 4.2 节在 Windows 上装固定版本，移植参考分支的适配器，
   逐个引擎跑同一基准并准备盲听样本。
2. 对照组：Qwen3-TTS 同模型提速（第 4 节 1–3 项），与第 1 步结果放在同一张表里。两者共用一张显卡，顺序执行。
3. 决策（用户试听后）：选定生产引擎（Qwen3-TTS 原生、VoiceStudio 中的某个引擎，或按 profile 都保留）；
   再按判定线决定先做实时还是整书。服务主体不变，见第 4.2 节架构决定。
4. 整书后台模式：电脑端任务队列 + 全书人物预扫 + 手机端提交整书、自动拉取、按书管理空间。
   借鉴 VoiceStudio 的按内容缓存与断点续跑思路，在自有服务中实现。
5. 实时模式（达标才做）：模型会话内常驻、首段优先、边播边生成，复用整书模式的任务队列。
6. 产品化：一键 Windows 包、模型可替换、真实注销登录自启验收。
